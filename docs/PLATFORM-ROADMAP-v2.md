# 自助爬虫平台改造产品规划

版本：v2.1 实施进度版  
日期：2026 年 11 月 5 日  
适用范围：当前仓库 `api`、`web`、`tests` 与 Docker Compose 部署

## 1 产品方向与版本边界

把现有“输入 URL 和 Prompt，抓取后导出”的工具，逐步改造成小团队可以持续使用的网页数据采集平台。优先解决账号隔离、重复运行、结果可靠性和使用成本，再扩展团队协作与开放集成。

首批用户按内部运营、研究分析和数据人员设计，管理员负责分配账号与资源。首版采用管理员创建账号的方式，不开放公众注册。面向外部客户的多租户 SaaS、套餐支付和大规模代理池留待实际业务验证后再建设。

当前已实现账号权限、HTML 发布，以及 P1 的任务中心、运行历史、周期调度、模板版本、单页试跑、字段校验、正文复用、失败重试和单次 Token 预算。具体升级与验收见 [P1 升级说明](P1-UPGRADE.md)，域名接入见 [网页发布部署说明](HTML-PUBLISHING.md)。P1 剩余资源治理和 P2 协作能力继续按下述目标推进。

## 2 当前能力与主要缺口

### 2.1 已有的可用基础

- 前端使用 Vue 3、Ant Design Vue、Vue Router，具有任务中心、新建抓取、结果与历史、采集模板和管理员用户管理页面。
- 后端使用 FastAPI、SQLAlchemy；生产部署使用 PostgreSQL、Redis、Celery。SQLite 支持本地开发与测试。
- 单页与同域全站抓取已接入 Scrapling；可限制深度、页数、并发，默认遵守 robots.txt。
- 页面内容能清洗成 Markdown；可以根据关键词筛选 AI 提取目标，支持长文分段提取与合并。
- 任务具有异步状态、进度、近期日志、停止、重新运行和删除操作。
- 结果可以查看正文、结构化内容，并导出 JSON、CSV、Markdown；缺少 AI 密钥时保留已抓取正文。

### 2.2 需要优先补足的产品能力

1. **用户级资源治理。** 已有单次运行 Token 预算，仍需用户每日任务、页面与 Token 配额，以及并发资源限制。
2. **运行观测。** 已记录运行与阶段耗时、近期日志、模型和用量，仍需持久化日志分页、费用配置与运营告警。
3. **数据资产。** 已有不可覆盖的运行快照，仍需跨运行的记录级变化检测、数据集及业务主键。
4. **团队授权。** 当前按账号隔离任务与模板，项目共享、项目角色和系统审计留待 P2。
5. **生产验收。** 已修复 CI 旧路径并启用真实检查，还需实际 PostgreSQL/Redis/Celery 联调、数据量性能基线与部署验收。

### 2.3 面向公网开放的准入条件

账号登录不能代替网络隔离。当前 URL 策略会阻止部分特殊 IP，但未覆盖私有网段、回环地址、DNS 解析与跳转链上的全部目标。受信任内部测试与公网开放应使用不同的网络访问策略。

在开放自助注册或不受信任用户提交 URL 之前，必须完成：解析后的 IPv4/IPv6 地址校验、每次重定向校验、Worker 出网隔离、域名与端口策略、响应大小与执行时间限制，以及用户任务和 AI 预算。公网配置默认禁止内网访问；内部确有需要时使用管理员维护的明确白名单。

## 3 用户场景与信息架构

### 3.1 核心场景

**运营收集竞品信息：** 选择产品信息模板，输入站点，预览少量页面的字段结果，确认后创建周期采集任务，查看新增和价格变化并导出。

**研究人员收集公开资料：** 输入多个授权来源，定义标题、作者、日期、摘要字段；对失败页面重试，按来源追溯原文，沉淀可复用的数据集。

**管理员维护团队：** 创建成员账号、调整权限、禁用离职账号；查看全局任务，发现异常费用和失败，控制并发与保留周期。

### 3.2 分阶段导航

- 当前版本：登录、任务中心、新建抓取、结果与运行记录、采集模板、用户管理、修改密码；计划和基本耗时在结果页管理。
- P1 后续：资源配额、日志分页、费用与告警。
- P2：项目空间、数据集、变更记录、通知与集成、审计与资源设置。

任务中心默认展示当前用户可访问的数据；管理员明确显示“全部任务”范围。权限不足时隐藏操作入口，同时由后端拒绝相同操作。用户直接访问其他成员的任务 ID 时返回 404，避免泄露任务是否存在。

## 4 P0 账号密码与用户权限

### 4.1 本次实现的范围

- 使用账号与密码登录，成功后进入任务大厅，支持回到登录前的站内页面。
- 不提供公开注册。初始管理员通过服务端命令创建，后续用户由管理员在用户管理页创建。
- 账号长度为 3–64 位，允许字母、数字、点、下划线、横线，统一转为小写；新密码为 12–128 位，允许长口令。
- 管理员可以新增用户、切换角色、启用或禁用用户、重置密码；禁止禁用自己或降低自己的管理员权限。
- 所有用户可以修改自己的密码，需要验证当前密码；修改后全部会话失效。
- 用户不能通过请求指定新任务的归属。用户 ID 保持稳定，权限判断不依赖可修改的展示名称。

### 4.2 角色与任务访问范围

**管理员 `admin`：** 查看、导出和操作全部任务，包括升级前没有有效用户归属的历史任务；管理用户账号；创建任务。

**普通成员 `member`：** 创建任务；查看、导出、停止、重新运行和删除自己的任务；不能访问其他成员任务或用户管理接口。

**只读用户 `viewer`：** 仅查看和导出归属于自己的任务；不能创建、停止、重新运行或删除。成员降为只读后仍可查看其历史任务。新建只读账号默认没有任务；团队共享与任务分配在 P2 建设，当前不向只读用户开放全平台数据。

这种设计首先保证个人数据隔离。需要多人共享同一批结果时，应建设项目成员与资源授权，避免把管理员权限当作共享权限使用。

### 4.3 登录与会话规则

- 密码使用独立随机盐和 PBKDF2-HMAC-SHA256，迭代 600,000 次；数据库和接口不保存或返回明文密码。
- 登录成功签发高随机性不透明 Bearer Token，服务端仅保存 Token 摘要与到期时间；默认有效期 8 小时，可配置为 1–168 小时。
- 浏览器使用 `sessionStorage` 保存会话 Token，API 通过 Authorization 请求头携带。关闭标签页通常会结束该标签页的会话存储，但服务端以撤销或到期为失效依据。
- 退出登录撤销当前会话；修改密码、管理员重置密码、调整角色或禁用账号撤销该账号的全部会话。账号被禁用后不能重新登录。
- 登录错误统一提示“账号或密码错误”，不区分不存在、禁用或密码错误。参数校验响应移除输入值，避免回显密码。
- 数据库记录登录限流，供多个 API 进程共享：同一账号每 15 分钟最多 10 次尝试，成功后清除该账号计数；同一来源地址每 15 分钟最多 60 次尝试，超限返回 429 与 Retry-After。
- 来源地址取直接连接地址，不信任任意客户端伪造的转发头。反向代理部署时应由可信代理配置真实来源识别，并根据团队规模评估共享出口的限流阈值。
- CORS 使用明确的前端来源列表，生产服务使用 HTTPS。Token 仍需要防范页面脚本泄露，后续配合 CSP、依赖维护与审计完善防护。

### 4.4 历史兼容与运维

升级新增 `users`、`auth_sessions`、`login_throttles` 表，不清空现有任务和结果，不把 `local` 历史任务自动分给普通成员。初始管理员可查看并管理这些任务。

使用 `python api/scripts/create_admin.py <账号>` 创建管理员，密码在终端交互输入，不设内置账号或默认密码，也不把密码放入命令行历史。Docker 使用 `docker compose exec api python scripts/create_admin.py <账号>`。

忘记密码时由另一位管理员重置；如果管理员全部无法登录，由有服务器权限的运维通过该命令创建一个不同账号名的恢复管理员，再在后台完成账号恢复。命令不会覆盖已有账号。

账号禁用会撤销平台访问，已排队或正在运行的采集任务会继续执行。需要停止消耗时，管理员应另外停止对应任务。账号删除、会话列表、首次登录强制改密和审计操作记录留待后续迭代。

### 4.5 P0 验收条件

1. 未登录调用任务和用户接口返回 401，健康检查仍可访问。
2. 两名普通成员互不可见对方的列表、正文、结构化结果和任何格式导出；停止、重跑、删除同样不能越权。
3. 即使提交其他用户的 `owner_id`，创建结果仍归当前登录用户所有。
4. 只读用户不能通过直接请求绕过页面权限限制；普通成员不能调用用户管理接口提升权限。
5. 登录、退出、过期、伪造 Token、错误密码、禁用账号、改密、重置密码和角色调整均有回归覆盖。
6. 启动已有数据库后旧任务保留；管理员可见，普通用户不可见。创建管理员过程不依赖短信、邮件或 AI 服务。

## 5 P1 稳定采集与重复使用

### 5.1 任务中心

- 增加任务名称、业务标签、状态、目标域名和创建时间筛选；默认分页，保存最近筛选条件。
- 区分“采集任务定义”和“某一次运行”。列表展示最近运行状态、下次执行时间、负责人和最近成功时间。
- 支持复制任务配置，新建时不修改原任务；危险操作继续保留明确确认。

验收：1000 条任务下分页查询稳定；筛选条件在翻页时保留；成员查询不能影响权限过滤。

### 5.2 调度与运行历史

- 新建 `task_runs`，每次执行保存独立 ID、配置快照、模板版本、开始结束时间、结果与消耗。
- 接入单一调度入口，支持单次、每天指定时间、每周指定日期；明确时区，默认 Asia/Shanghai。
- 支持暂停和恢复计划；展示下次执行时间。相同计划时间使用唯一键防止重复派发。
- 默认同一任务不重叠运行；上次未结束则跳过本次并记录原因。停机补跑策略首版设为恢复后仅运行最近一次，避免堆积。
- 手动重跑创建新的 run，不覆盖旧结果。失败页面支持单独重试，保留首次失败及重试记录。

验收：重启调度与 Worker 后不会重复执行同一计划；每次运行可追溯配置；旧结果可下载，任务取消可反映到运行记录。

### 5.3 采集模板与提取预览

- 把前端固定预设迁移为服务端模板，包含名称、使用说明、Prompt、输出字段、版本及可见范围。
- 用户创建任务前抓取 1–3 个样本页面，查看清洗正文与提取样例；预览也计入用户预算。
- 输出字段支持字符串、数字、布尔值、日期和数组，支持必填项。AI 结果校验失败时给出具体字段，不静默当作合格数据。
- 区分抓取失败、AI 失败、字段校验失败和部分成功；支持从已保存正文重新提取，避免重复下载页面。

验收：同一模板版本的字段定义稳定；预览与正式执行使用同一套清洗和校验逻辑；格式不合格结果可追溯并可重试。

### 5.4 可观察性与费用保护

- 记录排队时长、抓取/清洗/AI 阶段耗时、HTTP 状态、失败类型、页面数、Token 和模型名称。
- 为用户设置每日任务数、页数、并发数与 Token 预算；提交前预检，执行过程中计量，超限停止继续发起新请求并保留结果。
- 费用估算以模型价格配置与输入输出 Token 分开计算；供应商只返回总 Token 时显示可确定的用量，避免伪造精确金额。
- 日志按 run 分页保存并脱敏；告警覆盖 Worker 不可用、队列积压、连续失败、预算接近阈值。

验收：队列不可用时给出可理解提示；每次失败能定位阶段；重试计入成本；预算不能只靠前端控制。

## 6 P2 数据资产与团队协作

### 6.1 项目空间与授权

引入项目、项目成员和项目角色。平台角色负责系统管理，项目角色控制特定项目内任务和数据的访问。个人任务保持私有，用户通过明确操作迁入项目。只读成员可访问被授权项目的数据，无需获得全局管理员权限。

验收：一个用户可属于多个项目；跨项目越权测试覆盖详情、查询、导出、通知与 API；移除成员立即生效。

### 6.2 数据集与变化检测

- 从单次结果升级为数据集：定义字段、业务主键、来源 URL、首次采集时间和最后更新时间。
- 记录级去重与 URL 去重分别处理；支持按业务主键比较新增、更新、删除及字段变化。
- 对采集不完整的运行不能直接把缺失记录判断为删除；记录完整性条件与变化计算口径。
- 支持数据质量统计、筛选导出、人工标记异常、保留原始正文与提取版本。

验收：重复运行不会重复增加相同记录；价格变化可追溯到具体 run 和来源；失败采集不会产生大批误删提醒。

### 6.3 通知与开放集成

优先接入一种团队已有通知渠道，提供完成、失败和变更摘要；用户主动配置订阅范围。Webhook 有签名、重试上限与投递历史，禁止携带明文平台密钥。服务端 API 使用可撤销、可限定项目和操作范围的 API Key，限制频率并记录审计。

验收：通知与导出遵守同一套资源权限；同一变化事件不重复通知；失败投递可查询和重试；撤销 Key 立即生效。

### 6.4 管理与治理

补充账号及数据操作审计、结果保留天数、归档与恢复、备份验证、敏感字段脱敏。为公开服务补充邀请、恢复渠道、必要的多因素验证与反滥用策略。平台配额、资源隔离和费用控制成熟后，再评估收费套餐与对外注册。

## 7 手机号验证码登录的选择

### 7.1 结论

技术上可实现，核心接口不复杂；完整上线的工作集中在短信通道、审核、费用与滥用防护。现阶段以内部小团队为主，账号密码加管理员分配账号更适合当前投入。若后续出现大量外部个人用户、邀请转化需求或手机触达需求，再引入手机号登录。

账号密码不需要购买短信服务，便于私有部署和离线环境；手机号验证码能降低记忆密码的负担，但依赖送达率、供应商可用性和持续发送成本。邮箱邀请或企业统一登录也可以作为面向团队的候选方案，需结合现有账号体系选择。

### 7.2 若接入短信，需要一起建设的能力

1. 选择短信供应商，开通账户并准备资质、短信签名和验证码模板。以阿里云中国大陆短信为例，签名和模板审核通过后才可发送；审核材料与时长以供应商当时要求为准。
2. 新增发送验证码与校验登录接口。验证码建议有效期 5 分钟，一次性消费；只存摘要，不记录到日志，不在响应中返回。
3. 建议同一手机号发送间隔至少 60 秒，单验证码校验错误最多 5 次，同时按手机号、来源地址、设备风险、日发送总量设置限制。具体阈值需根据实际转化与滥用情况调整。
4. Redis 原子完成校验、错误次数累加和消费，防止同一个验证码并发重复换取会话；Redis 不可用时停止验证码登录，不能跳过校验。
5. 设置供应商预算上限、监控发送量与成功率、告警短信轰炸，保留密码登录作为管理员应急入口。
6. 手机号唯一绑定到稳定用户 ID；已有账号绑定手机号时需要验证当前身份和新手机号。换绑、号码回收、账号合并、手机号脱敏、短信超时与重试都要有产品规则。
7. 首版即使使用短信，也继续采用邀请制或管理员开通，避免“收到验证码即自动注册并获得采集资源”。短信验证不能代替角色与任务权限。

### 7.3 投入判断

以下为单名熟悉当前技术栈工程师的开发粗估，不含供应商审核等待：账号密码及权限约 3–5 个工作日；短信验证码及必要频控、绑定和异常流程额外约 3–6 个工作日。公开注册、风险验证、多通道容灾与运营告警会进一步增加工作量。这是排期参考，不是已投入工时或固定交付承诺。

## 8 技术演进与发布顺序

保留 Vue 3、FastAPI、PostgreSQL、Celery 与 Scrapling，先在现有结构中完善边界。当前业务规模没有证据表明需要拆成大量微服务。

推荐数据实体演进：`users` 与认证会话 → `tasks` 与 `task_runs` → 模板和字段定义 → 数据集和记录版本 → 项目成员、通知与审计。每次变更都配数据库迁移与备份恢复方案，保留既有 ID 和结果，不用删除数据卷升级。

以下按一名全栈工程师、需求稳定、已有可用测试环境估算，阶段依赖前一阶段的关键数据模型与权限验收：

- **P0 账号与权限，约 1 周：** 完成本次功能联调、管理员初始化、历史数据兼容与部署验证。上线前配置 HTTPS、明确前端来源，验证真实数据库备份。
- **P1 稳定采集，约 2–3 周：** 优先运行历史与调度，再做模板预览、校验和成本保护。发布前修复 CI 旧路径并启用真实测试。
- **P2 团队与数据集，约 3–5 周：** 先项目授权与数据集，再做变化检测及一种通知渠道。
- **P3 外部服务化，按需求另行评估：** 公网抓取边界、短信/企业登录、多租户资源隔离、套餐等，以用户需求和运行指标为依据。

建议以每期验收条件作为发布门槛，先交付可以单独使用的小版本。避免将大屏、代理市场、支付和多个短信供应商塞进第一期。

## 9 产品指标与验证方法

以下是建议的内部试运行目标，尚未进行线上测量。试运行首周先采集基线，再按目标网站类型调整。

- 首次成功：用户拿到账号后，在配置好采集与 AI 服务的前提下，10 分钟内完成一个单页示例并导出。
- 访问控制：权限测试中的匿名访问、跨用户访问、只读写入、旧会话复用全部被拒绝。
- 执行可靠性：固定授权样本站点集的页面抓取成功率目标不低于 95%，分别统计被 robots 拒绝、站点不可用、反爬与系统错误。
- 提取质量：选取至少 50 个业务样本，由人工标注字段真值；必填字段完整率目标不低于 95%，另行统计准确率，避免只用 JSON 可解析率代替质量。
- 运行可解释性：每次失败均可定位到 run、阶段、目标页面和错误原因；不在日志暴露密码、Token 或模型密钥。
- 费用可控：达到预算后不再派发新的消耗请求；已发出的在途请求单独计量，报告实际超限量。
- 数据保护：发布前完成一次包含任务、结果、用户和会话数据的备份恢复演练，明确恢复后是否统一撤销旧会话。

## 10 第一轮试用要验证的业务假设

默认假设是小团队内部使用、管理员开通账号、以授权公开网页为主要来源。试用时优先记录：最高频的两类采集场景、每日任务与页面规模、真正需要的字段、定时频率、是否共享结果、是否必须采集登录后的页面，以及可接受的 AI 成本。

如果主要需求是内部协作，优先项目授权与企业登录；如果主要需求是外部个人自助使用，再提高手机号验证、邀请转化和费用配额的优先级。先用实际任务验证采集与结果价值，再决定登录渠道和商业化投入。
